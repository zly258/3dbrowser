# 大模型内存优化 · 分阶段实施计划

> 版本：v1（2026-11-13）  
> 当前基线：v1.9.1（`5287624`，本地已提交、未推送）  
> 规则：**只在本地提交，不 push、不同步远程**；每一步必须先跑回归测试，通过后再提交下一步。

---

## 1. 目标与非目标

### 目标

在 4GB 级 JS 堆内，让同一份大模型（当前测试模型：2.9GB NBIM / 1271 分块 / 231.4K 构件 / 52.51M 面）满足：

1. 可加载、可浏览（旋转/平移/缩放不卡死）；
2. 模型结构、单选、高亮（含发光）、框选、属性面板、属性搜索、显示样式全部不退化；
3. 概览视角能看到**完整模型**（不是 1/3 实体 + 大面积 ghost 骨架）；
4. 内存稳定，不随浏览时间增长；删除模型能回收内存；
5. 旧格式（NBIM v8）与 LMB 直读继续可用。

### 非目标（本阶段不做）

- 不做 WebGPU 版 Nanite（cluster DAG + GPU 驱动）——留作 P3，视 S6 结果再评估；
- 不改 UI 布局与交互流程；
- 不改变 NBIM 的 v8 读取路径（v9 只新增，不破坏 v8）。

## 2. 约束与提交策略

- 分支：继续在 `main` 上本地提交（当前 `main` 已领先远程 1 个提交，保持不推送）。
- 每个步骤一个独立提交，前缀：`perf(mem): ...` / `feat(nbim): ...` / `docs(mem): ...`。
- 每个步骤完成后：
  1. `npx tsc -p tsconfig.lib.json --noEmit --skipLibCheck` 通过；
  2. `npm run build` 通过；
  3. 按 [回归清单](testing/regression-checklist.md) 跑一遍；
  4. 把结果写进本文 §9 进度表 + 提交信息；
  5. 通过后再进入下一步。
- 任一测试失败：先修复；无法修复则 `git revert` 该步提交并记录原因。

1. **每块字节数**（当前 6.5MB，其中至少 2 份几何数组副本）→ P1；

## 5. 分步计划

### S0 · 基线固化与度量（0.5 天）

**目的**：后面每一步都有可比较的数字，避免“感觉快了”。

**改动**

- `SceneManager.getMemoryReport()`：返回分类字节统计
  - `chunks`：总数/已加载/处理中/读缓存块数与 MB、`chunkResidentBudgetMB`
  - `geometry`：`optimizedMapping` 条目数、各 BatchedMesh 合并缓冲估算（position/normal/index 字节）、CPU 侧源数组估算
  - `instances`：实例数 × 每实例元数据估算
  - `edges`：`displayEdges` 对象数与顶点字节
  - `properties`：文档数、行数、估算字节
  - `structure`：结构树节点数
  - `heap`：`usedJSHeapSize` / `jsHeapSizeLimit`
- `window.__viewer` 调试钩子：仅在 `?dshDebug=1`（或 dev host）时挂 `SceneManager` 实例，便于自动断言。
- 把测试子集生成脚本从 `preview-tmp/` 移到 `scripts/make-test-subset.mjs` 并写用法。
- 新建 [回归清单](testing/regression-checklist.md)。

**验收**

- 控制台/接口能输出上述分类；
- 200 块子集与全模型的基线数据记录进 §9；
- 不改变任何现有行为（无功能提交风险）。

**提交**：`perf(mem): 增加内存分类统计与回归测试基线`

---

### S1 · 读缓存按字节上限与并发写回修复（0.5 天）★ 第一刀

**问题**：`putChunkReadCache` 只按“条数”淘汰，且并发读取时每个 `put` 都用调用前拿到的
`chunkReadCacheOrder` 快照回写；最后写入者覆盖 order，其它条目失去顺序记录、永远不会被淘汰。
实测全模型缓存了 **410 条 / 943MB**（配置上限本应是 96 条）。

**改动**

- `chunkIO.ts`
  - 缓存按 `ArrayBuffer.byteLength` 计费，新增字节上限（默认 128MB），条数只作兜底；
  - `putChunkReadCache` 不再依赖外部 order 快照，写入后**从 map 重建 order**（或在调用侧串行化写回）；
  - 淘汰策略：LRU，直到 `bytes <= limit`；
  - 命中时不再 `buffer.slice(0)` 复制整块（只复制一份给 worker 传输，缓存保留原件）。
- `SceneManager`
  - 新增 `chunkReadCacheBytes` 配置并纳入 `setChunkOptions`；
  - 并发读改为“先读文件 → 再串行写缓存”，避免多请求同时覆盖 order；
  - `getMemoryReport()` 增加 `readCacheBudgetMB`。
- `chunkRuntime.ts`：默认 `chunkReadCacheMB: 128`。

**验收**

- 200 块子集：读缓存 ≤ 128MB（基线 411.9MB），堆 ≤ 1.0GB；
- 全模型：读缓存 ≤ 128MB（基线 943MB），堆下降 ≥ 700MB；
- 相机移开再移回时仍能命中缓存、不重复读盘；
- 回归清单 L/M/P/B/A/V/D/E 全过。

**风险**：缓存过小会让“卸载后重载”变慢；128MB 起步，若重载明显变慢再调。

**提交**：`perf(mem): 分块读缓存按字节限流并修复并发写回`

---

### S2 · 释放 CPU 侧几何副本（1–2 天）★ 收益最大

**问题**：`reconstructBatchedMeshFromWorkerData` 把 worker 解出的 `BufferGeometry` 通过 `BatchedMesh.addGeometry()` 拷进合并缓冲，同时把源 `BufferGeometry` 挂在 `mesh.userData.batchIdToGeometry` 上供拾取/高亮使用 → 同一份几何在堆里存两份。

**改动**

- `chunkMesh.ts`
  - 不再保存 `batchIdToGeometry`；改为：
    - `batchIdToGeometryId: Map<instanceId, geometryId>`（`batchedMesh.getGeometryIdAt`）
    - `batchIdToUuid` / `batchIdToColor` 保留
  - `addGeometry()` 完成后对源 `BufferGeometry` 调 `dispose()` 并解除引用，让 worker 数组可回收。
- `chunkResources.ts`（`registerOptimizedMeshResourceMapping`）
  - mapping 条目从 `{ mesh, instanceId, originalColor, geometry }` 改为 `{ mesh, instanceId, geometryId, originalColor }`。
- `highlight.ts`
  - `getFocusedInstanceBounds`：用 `getGeometryIdAt` + `getBoundingBoxAt(geometryId)` + `getMatrixAt` 计算，不再用 geometry。
  - `updateHighlightGlowMesh`：改为 **零拷贝视图**——position/normal 用合并缓冲 `subarray(vertexStart*3, …)`，索引按 `vertexStart` 重定基后只拷贝该实例的索引（几 KB）。
- `picking.ts`（矩形框选）
  - 用 `getGeometryIdAt` + `getBoundingBoxAt` 代替 `batchIdToGeometry`。
- `renderTargets.ts`（`collectRenderableBoundsForIds`）
  - 用 mapping 的 geometryId + bbox。
- `SceneManager.updateHighlightGlowMesh` / `clear` / 删除路径同步调整；`unregisterOptimizedMeshMapping` 不再持有 geometry。

**验收（硬指标）**

- 200 块子集稳定堆：**≤ 1.0 GB**（基线 1.39 GB，降 ≥28%）；
- 全模型可常驻块数：**≥ 600**（基线 ~410）；
- 单选/高亮颜色/发光/框选/属性/结构树/三种样式全部通过；
- 内存不随时间增长；删除模型后堆明显回落。

**风险与回滚**

- 风险：发光几何视图的索引重定基错误 → 发光错位。测试必须覆盖：单选后截图 + 像素校验高亮、发光 1.5s 内截图。
- 回滚：`git revert` 本步提交，功能回到 v1.9.1。

**提交**：`perf(mem): 释放分块源几何副本，按 geometryId/包围盒拾取高亮`

### S3 · 远景边线按需（0.5 天）

**问题**：`DisplayEdgeBuilder` 为每个加载块生成一整份边线顶点；真实/线框模式下等于第二份几何。

**改动**

- 只对“近处/屏幕占比足够”的分块生成边线；距离变远时释放，拉近时按需重建（带缓存上限）。
- 线框模式保持全量（否则模型会缺线）。
- `displayEdges` 增加字节统计，纳入 `getMemoryReport()`。

**验收**

- 三种样式视觉正确；
- 真实模式 200 块子集堆再降 ≥15%；
- 旋转/缩放时边线不闪、不丢近景轮廓。

**提交**：`perf(mem): 远景分块边线按需生成与回收`

---

### S4 · 固定开销瘦身（1 天）

**问题**：首个分块前已占 ~635MB；大头是 23 万条属性文档、结构树与材质。

**改动（按测量结果取舍）**

- `nbimPendingDocs`：改成紧凑存储（key 字符串驻留 + 行数组化），或按需从 manifest 原始区段解析；
- 属性名索引/搜索文档：加载后释放中间 JSON 字符串与重复对象；
- `chunkReadCache`：按字节上限而不是块数（例如 128MB）；
- 结构树：评估是否需要对 23 万节点做惰性构建（与现有 `deferredStructureThreshold` 对齐）。

**验收**

- 基线的“首个分块前已用堆”≤ 400MB；
- 属性面板、属性搜索、定位、导出不退化；
- 200 块子集首次可交互时间不增加。

**提交**：`perf(mem): 压缩属性文档与固定开销`

---

### S5 · 流式池硬化（1 天）

**改动**

- 预算统一为**字节池**：`residentBytes / budgetBytes`，块数仅作二级约束；
- 请求优先级打分：屏幕占比、中心度、距离、最近可见时间、是否聚焦；
- 请求可取消（快速移动/切换模型时）；
- 超预算降级顺序：先降 LOD/跳过远景 → 再淘汰不可见 → 最后才淘汰可见最远；
- 预取窗口按字节而不是块数。

**验收**

- 全模型连续旋转/缩放 60s：CH 稳定、堆稳定、无 92/93 抖动、无报错；
- 平移后新区域能在 1–2 帧内开始出实体；
- 单元：`chunkLifecycle` 模拟脚本（预算内稳定、无振荡）。

**提交**：`perf(streaming): 字节预算与优先级流式池`

### S6 · 预算校准与全量驻留（已完成）

S5 之后每块真实足迹约 **2.06MB**（名义几何 1.556MB），而预算仍按 2.0 倍估算，
导致堆只用 72%、常驻被压在 820 块。把 `CHUNK_FOOTPRINT_MULTIPLIER` 校准到 **1.32** 后：

- `totalDecodedMB × 1.32 ≈ 2611MB` < 预算 2697MB → `fitsAll` 成立
- **1271/1271 全量驻留**，GC 后堆 **3302MB（79%）**
- 连续旋转/缩放 60s+：CH 恒 1271、堆 3335–3365MB 无增长、无 92/93 抖动
- 点选/框选/属性/结构树全部正常

### S7 · 量化压缩（法线 int8 已完成；v9 文件格式待做）

**格式（向后兼容 v8）**

- position：int16 + 每块 `scale/offset`（3×2 float32）；
- normal：oct16（2×int16）或 8-bit 量化；
- index：顶点 <65536 用 uint16，否则 uint32；
- 分块 payload：zstd/brotli（导出端压缩，运行时 `DecompressionStream` 或 WASM 解压）；
- manifest 增加 `version: 9`、每块 `encoding` 字段；v8 分支保持不变。

**改动**

- `nbimBatchConvert`：导出 v9；
- `SceneManager`/`chunkWorker`：按版本分派解码；
- 兼容：v8 文件继续按现有路径加载。

**验收**

- 同模型文件体积 ↓ ≥50%；
- 同分块数下堆占用 ↓ ≥40%；
- 视觉与 v8 无明显差异（截图对比）；
- 单选/框选/属性/结构树/三种样式通过。

**提交**：`feat(nbim): v9 量化压缩格式（兼容 v8）`

### S8 · 每块粗 LOD / HLOD（2–3 天）

**目标**：概览时 1271 块全部“有东西可看”，不再大面积 ghost。

**方案（先做 A，B 视效果）**

- **A. 每块粗模（推荐先做）**
  - 导出端为每块生成 LOD1：三角形 10–20%，位置/法线可进一步量化；
  - 运行时按屏幕误差选 LOD：远景只驻留 LOD1，近景换 LOD0；
  - 拾取/框选/属性仍映射到实例（LOD1 的实例表与 LOD0 相同）。
- **B. 块级 HLOD 盒体**
  - 若 A 成本过高，先用每块合并 bbox 实体（低多边形盒子）占位，近景换实体。

**验收**

- 全模型概览：可见分块数 = 1271（粗模），堆 ≤ 3GB；
- 拉近后自动精化；单选/框选/属性/结构树正常；
- 粗模切换无闪烁、无重复加载。

**提交**：`feat(nbim): 分块粗 LOD 与屏幕误差选择`

## 7. 度量方法

- 堆：`performance.memory.usedJSHeapSize / jsHeapSizeLimit`（每次测试前 `HeapProfiler.collectGarbage`）。
- 常驻：状态栏 `CH x/y` + `getMemoryReport().chunkLoadedCount`。
- 分类：`getMemoryReport()`（S0 引入）。
- 首帧/交互：`performance.now()` 打点（S0 记录）。
- 高亮正确性：截图前后像素对比（红/绿主导像素数），沿用当前验证方法。

|---|---|---|
| 释放几何后拾取/发光失效 | 核心功能退化 | S2 验收强制覆盖单选/高亮/框选/发光像素校验；失败即回滚 |

| 粗 LOD 与实例映射错位 | 点选错对象 | 保留实例表不变，仅替换几何与索引 |
| GC 不及时导致测量抖动 | 误判收益 | 每次测量前 CDP GC，取 3 次稳定值 |
| 长时间本地提交偏离远程 | 后续推送冲突 | 每个提交保持单一主题，最后统一合并 |
